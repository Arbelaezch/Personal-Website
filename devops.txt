3. DEPLOYS (GitHub Actions: .github/workflows/main.yml)
=====================================================================
Push/merge to main -> tests (migrations check, check --deploy, test suite with coverage) -> deploy job:
SSH to christiandonovan.ca as carb -> fast-forward pull -> pip install -r requirements.txt -> migrate ->
collectstatic -> restart gunicorn -> health check of / and /api/v1/recipes/ through nginx.
If anything fails the CODE is rolled back to the previous commit (migrations are NOT rolled back, so keep
them backwards compatible) and the job fails (GitHub emails the failure).
  * The server pulls from GitHub with ~/.ssh/github_deploy_key (carb's ~/.ssh/config, verified host keys).
  * The deploy itself only needs "sudo systemctl restart gunicorn" and installs no system packages, but carb's
    passwordless sudo rule is still broader than that (it includes apt-get install *; tracked in the sudoers
    issue). Needed once on a new server:
      sudo apt-get install -y python3-venv python3-dev pkg-config default-libmysqlclient-dev build-essential
  * Recreate the venv:  cd /var/www/portfolio && python3 -m venv env && env/bin/pip install -r requirements.txt
  * Static files: collectstatic never deletes files from removed packages. Remove stale directories by hand
    from staticfiles/ and RESTART gunicorn afterwards (WhiteNoise indexes the folder at startup; until the
    restart it answers 500 for the deleted files).
Manual deploy / restart:
  sudo systemctl restart gunicorn        # after daemon-reload if the unit changed
  sudo systemctl status gunicorn ; journalctl -u gunicorn -n 50

4. NGINX  (deploy/nginx/, see its README)
=====================================================================
Edit the files in deploy/nginx, then on the server:  sudo deploy/nginx/install.sh
(backs up /etc/nginx, tests, reloads, restores the backup if the test fails).
Layout: one file per site in sites-available/, shared snippets (security headers, proxy settings that OVERWRITE
X-Forwarded-For, Cloudflare real-IP), 000-catch-all (unknown Host -> 444, unknown TLS name -> refused),
rate limits in conf.d/00-global.conf. New site: templates/app-site.conf.template.
  sudo nginx -t ; sudo systemctl reload nginx ; sudo tail -f /var/log/nginx/error.log

5. SERVICE USER AND SANDBOX (copy for every new app)
=====================================================================
  * gunicorn runs as system user "portfolio", not an admin:
      sudo useradd --system --user-group --no-create-home --home-dir /nonexistent --shell /usr/sbin/nologin <app>
  * Code, venv and staticfiles belong to the deploy user and are only readable by the app; the app may write only
    its media dir (owner = app user, group www-data so nginx can read).
  * .env: owner carb, group <app>, mode 640 (it holds the DB password). Never world-readable.
  * Socket: SocketUser/Group=www-data, mode 0660, so only nginx can reach gunicorn.
  * systemd sandbox: NoNewPrivileges, PrivateTmp, PrivateDevices, ProtectSystem=strict with ReadWritePaths limited
    to media, ProtectHome, kernel/cgroup/clock protections, empty capability set. gunicorn 26 also needs
    --no-control-socket (it would otherwise try to create a socket in the non-existent home).
  * Versioned units: deploy/systemd/gunicorn.service and gunicorn.socket. Install: copy to /etc/systemd/system/,
    sudo systemctl daemon-reload, sudo systemctl restart gunicorn.socket gunicorn.
  * Check:  ps -o user,cmd -C gunicorn ; systemd-analyze security gunicorn

=====================================================================
8. UPDATES
=====================================================================
  * Security updates are automatic; kernel updates need a reboot:  ls /var/run/reboot-required
    (headless: check it periodically, reboot in a quiet moment, then verify the site and the services).
  * OS upgrades go through do-release-upgrade inside tmux with fresh backups first. 22.04 -> 24.04 was done on
    2026/11/10 (sshd was unreachable on :22 for about 20 minutes mid-upgrade, which is normal).
    After an upgrade, diff /etc against the backup (the upgrade silently dropped the Samba share).
  * Python packages: requirements.txt pins exact versions; use releases that are at least 14 days old and carry
    the security fixes. Django stays on 5.2 LTS until MySQL is 8.4+ (see the Django 6 issue).
